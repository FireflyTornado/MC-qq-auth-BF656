# 系统架构

## 组件与部署

```text
QQ 群 → NapCat → NoneBot2 → SQLite
NoneBot2 ── 提交后 POST 通知 ──→ FastAPI ←── 只读数据 ── SQLite
FastAPI ── HTTPS 快照 / WSS 更新提醒 ──→ Minecraft 插件（计划接入）
```

NapCat、NoneBot2 和 FastAPI 通常部署在同一台主机。NoneBot2 使用 OneBot v11 WebSocket 客户端连接 NapCat，接收目标群的消息和事件。Minecraft 运行在异地主机，计划由插件通过受控的 HTTPS/WSS 入口接入授权 API。反代访问边界见 [部署说明](deployment.md)。

## 写入与授权版本

`/绑定` 和 `/解绑` 经过目标群过滤，将同步 SQLite 操作交给工作线程。`offline_bindings` 保存当前离线服绑定，每个群内的 QQ 只能有一条有效绑定，小写游戏名全库唯一。`/我的绑定` 读取有效记录，返回原始大小写。解绑删除对应的有效绑定。

绑定和解绑使用 `BEGIN IMMEDIATE`，在同一事务中写入授权记录并更新 `auth_state` 的 `id = 1` 单行。版本为整数，计算方式为 `MAX(旧版本 + 1, 当前 Unix 毫秒)`，同毫秒内写入或时钟回拨时仍可递增。版本行更新失败时，绑定变更也会回滚。SQLite 是授权状态的数据源，迁移由 `bot/migrate.py` 管理，已有绑定和版本会保留。

## 提交、通知与快照

1. SQLite 提交成功后，Bot 才使用独立的 Notify Token 调用 `POST /internal/mc/notify`。网络故障不影响已提交的数据。
2. FastAPI 从 SQLite 读取最新版本。版本变化时向当前进程中已连接的客户端发送 `auth_updated`，消息包含版本号。API 还每 60 秒读取版本，补偿未成功送达的内部 POST。
3. `GET /internal/mc/snapshot` 在一个只读事务中读取版本号和目标群的有效小写名单，确保一次响应里的版本与名单来自同一数据库快照。

当前 WebSocket 连接与广播去重状态保存在 API 进程内。通知适合触发刷新，断线期间的消息不会补发。`delivered` 统计当前进程完成发送的连接数，客户端是否取得并应用快照由客户端自行处理。

## 计划中的 Minecraft 同步

当前 Java 插件只提供基础生命周期、默认配置和状态命令。后续同步客户端应在首次连接和每次重连后拉取完整快照，将快照版本与名单一起更新到本地缓存。收到更新提醒时按需刷新，并处理读取快照期间到达的更高版本提醒。这样即使丢失更新消息，客户端也能恢复到当前授权状态。连接或快照失败时，准入策略与缓存时效需在实现强制模式时明确。

QQ 入退群监听目前只在日志中记录目标群事件。自动解绑需要接入同一撤销事务，并验证真实事件投递和重复事件处理。在线踢出还需要 Minecraft 插件具备授权同步和撤权执行能力。
